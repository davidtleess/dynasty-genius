```

`outcome_returned` was added to `ENGINE_B_OUTPUT_COLUMNS` on 2026-08-31 in `58d3b20c`. The seed
carries it. **The table the product actually serves still does not, three days later.**

Cause: consumers read the RUNTIME csv (`resolve_feature_source`, `src/dynasty_genius/features/
feature_source.py:66-119`, prefers the published runtime whenever present), and the runtime is only
rebuilt when `compute_source_hash` changes (`feature_refresh_runner.py:33-63`). That hash covers
loader frames, the seasons window, the nflreadpy version, TE artifact hashes and a two-key
`_builder_config` — **it does not cover the assembly code or `ENGINE_B_OUTPUT_COLUMNS`.** So a
code-only schema change leaves the hash unmoved, the 09:00 runner reports `status: noop`
(`app/data/features_runtime/feature_refresh_latest_report.json`, generated 2026-08-31T13:00:44Z),
writes nothing, and the change appears days later when upstream frames finally move — near-certainly
at kickoff **2026-09-10**.

**What survives, verified at `feature_refresh_runner.py:44-58`:** the hash payload is
`seasons_window`, `package_version`, `builder_config`, `te_rubric_artifacts`, `identity_inputs`,
`stream_provenance` and `loader_outputs`. **It does not cover the assembly code or
`ENGINE_B_OUTPUT_COLUMNS`.** So a code-only schema change still does not trigger its OWN rebuild.

**What that actually means — the corrected version:** the change rides along on the next
DATA-triggered rebuild. In season the upstream frames move daily, so that is the next morning, not
a distant event. The hazard is therefore not "it never arrives" but **"its arrival is decoupled from
its land"**: a schema change is invisible on landing day and appears on someone else's morning, with
no commit that day to explain it.

**Consequence for anyone verifying a schema change:** checking after landing and seeing no movement
is NOT evidence of inertness, and checking later and seeing movement is NOT evidence that day's work
caused it. Read the runtime CSV's column count and its mtime together — neither alone is a claim.

**For DG-127 specifically:** expect `games_t_minus_*` in the served runtime at the first
data-triggered refresh after it lands — plausibly the next 09:00 run, NOT kickoff 09-10 as this
entry originally said. It changes no served value either way (carried, not consumed).

## 3. `games_t_minus_1` / `_minus_2` are LEFT-CENSORED at 4 games

`feature_assembly.py:178` drops player-seasons with `games_t < MIN_GAMES_THRESHOLD` (4) **before**
the step-7 lag join. A 1–3 game prior season is therefore written NaN/`_available = False` —
byte-identical to a player who was never in the league. Confirmed on real data: minimum observed
`games_t_minus_2` across the 2025 inference set is **5.0**, never below 4.

The lags separate a FULL prior season from NO prior season. They cannot separate a SHORT one from
none. **A taper that reads absence as "no NFL history" will be wrong about exactly the injured
players it most needs to judge.** Pinned by
`tests/contract/test_feature_engineering_extraction.py::test_games_lags_are_left_censored_at_min_games_threshold`
so DG-128 cannot assume otherwise. The same censoring already applies to the ppg and snap_share lags.

**6a. The guard that caught it is not a partition guard.** `build_universe_pvo_batch.py:281-285`:

```python

    prediction_duplicate_count += 1
    continue

It compares prediction VALUES. **Equal predictions are counted as duplicates and pass silently.** It
fired only because one player's 2018 and 2025 predictions happened to differ. A widened partition
whose duplicates produced equal predictions would pass clean. This is a value-collision guard
standing in for a partition assertion that does not exist. Assert the partition is exactly one
season and non-empty; do not rely on this.
