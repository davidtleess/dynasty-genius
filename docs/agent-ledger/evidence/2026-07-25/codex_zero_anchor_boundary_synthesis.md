## Unprompted first-pass convergence

All three independently produced the same core structure:

1. Tickets may require observable outcomes.
2. An internal technical restriction can be binding only when it comes from an independently established or owner-ratified boundary, carries its reason, and is not merely the ticket author's preference.
3. Named tools, libraries, code topology, work sequence, and test method default to developer choice.
4. Unsupported internal restrictions are removed, made nonbinding, or left unresolved.
5. David's original standard supplies the principle but is **not operationally sufficient for edge cases**. All three said the owner must define which sources of authority count and what evidence a ticket must carry.

This is a clean convergence because none of those elements was supplied in the prompt beyond David's own “what and why, not exact how” standard.

## What David still has to decide

The fresh evidence does not honestly produce a complete final sentence without an owner ruling. It isolates the missing decisions:

1. **Authority sources:** Which pre-existing sources can make an internal restriction non-negotiable—law, external contract, security policy, architecture, repository governance, direct David ruling, or some subset?
2. **Evidence burden:** Must a ticket cite that source and state the consequence protected, or is an uncited assertion enough?
3. **Process placement:** Do RED-first and independent-review requirements belong inside every engineering ticket, or once in a program-wide Definition of Done?
4. **Methodological particulars:** Is a pinned seed an acceptance input or a developer-selected reproducibility mechanism?

Until David answers those, a stranger can apply the clear cases consistently but cannot resolve every edge without asking.
