### ⚠️ FIRST, A RETRACTION — the morning's alarm was mine, not the product's

At 06:15 the nflverse capture failed (exit 1) on its first ever scheduled fire. I reported to
David that the failure had destroyed the morning's NFL statistics. **That was wrong, and he

What actually happened: the twelve season streams fetched, found their records **byte-identical**
to the stored vintage, and correctly wrote nothing. `apply_season` returns `"unchanged"` before
it writes when the content digest matches, **and does not update `nflverse_capture.ingested_at`
on that path**. So the Aug 8 database mtime and the Aug 5 ledger date are the *signature of a
healthy idempotent capture*, not evidence of loss. Proof, rerunnable:

```
python - <<'PY'
import json
a=json.load(open('app/data/nflverse_usage/raw/ngs_passing_2023_<older>.json'))
b=json.load(open('app/data/nflverse_usage/raw/ngs_passing_2023_<newer>.json'))

PY
```

Only `captured_at` differs between runs. Identical file SIZES with differing sha256 is the
fixed-width-timestamp signature, not changed data.

was new; (2) contracts vetoed the whole run — `apply_season` commits per stream-season on its own

### ✅ SHIPPED (uncommitted, awaiting David's word on committing)

**Move 1 — an unpublished season is a recorded skip, not a failure.**
`_unpublished_season_bound()` reads the source's OWN bound off its refusal and records
`skipped: "not_yet_available"` with `source_bound`, mirroring the existing `before_min_season`
branch. Deliberately narrow — a season BELOW the bound, a message naming no bound, and any
non-`ValueError` all still fail the run.
*Why read the bound instead of declaring `max_season`:* a hardcoded bound is a code edit due the
week the season starts — in-season, after the 2026-09-04 freeze, when only Tier 0 lands. Reading
it means **week 1 opens the season with no code change at all.**

**Move 2 — the scheduled job asks for the current league season, derived.**
`current_league_season()` / `default_capture_seasons()` in `nflverse_usage.py`;
`scripts/run_nflverse_usage_capture.py` `DEFAULT_SEASONS` now calls it. Was the literal
`(2023, 2024, 2025)`. The LaunchAgent passes no flags, so that default IS the schedule.
Derived so no annual edit is ever due. The March boundary can flip ~2 weeks early, which is safe
**by construction** because Move 1 records an early flip as a skip. The two guards compose.
This turns on **2026 depth charts** — the one stream with live 2026 data, updating daily through
cutdowns, carrying `pos_rank`/`pos_slot`. `DEPTH_CHARTS` already declares
`eras=(DEPTH_WEEKLY_ERA, DEPTH_DAILY_ERA)` and `_DEPTH_DAILY_COLUMNS` is an exact match for the
12 columns 2026 returns; era selection is shape-driven (`requires=("dt",)`), not season-keyed.
**No era work was needed — the machinery was already built for this.**

### ❌ MOVE 3 PROPOSED, IMPLEMENTED, THEN REVERSED — I was wrong

I proposed decoupling `publish_export()` from stream failure so a contracts refusal could not
freeze the export, and David approved it. Implemented; **two existing contracts went red**:

- `test_nflverse_usage_ingestion_red.py::test_a_failed_capture_leaves_the_previous_export_untouched`
- `test_contracts_ingestion_red.py::test_a_capture_failure_preserves_the_prior_snapshot`

They encode a **last-good handoff**: *"A consumer must keep reading the previous complete vintage
rather than a half-written one."* `publish_export`'s own docstring records that this invariant
preserved the consumer commit point during a live 2026-08-08 failure. The frozen export is that
invariant **working**, not a bug. Advancing it on a failed run publishes a vintage where some
streams are fresh and others stale, with nothing telling a consumer which.

**Reverted in full; both files back to green.** The tests caught the error, which is the system
working. The genuine fix is per-stream quarantine (isolate the failing stream, keep the vintage
complete for the rest) or a separately-named degraded marker consumers opt into — **neither is
in this sprint's 8.5 committed days and both need David's word.** Left as a filed finding.
