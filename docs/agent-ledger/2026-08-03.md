Both survivors were genuine, in load-bearing code:

- **`matches`: `==` → `<=` survived.** For sets that is subset, so the mutant still refuses an
  *additive* column — all the B1 control ever exercised — while nothing pinned the other half of
  the declared contract, that a **missing** column also refuses.
  **Scope corrected by Codex, then measured.** I first called this silent data loss. It is not.

  guards catching the consequence.
- **`_projection_fingerprint`: `sort_keys=True` → `False` survived.** Capture identity would have

Both are closed, and round 2 proves it. Full artifact, per-mutant census, runner and limitations:

### A wrong root cause I published, and Codex's correction

The first exec returned **12/12 SURVIVED**. I flagged it as the signature of a vacuous harness,
hand-applied the line-195 mutation, watched the suite kill it, and concluded **cosmic-ray `exec` is
broken on Python 3.14** — telling David the tool's output could not be trusted here.

**Wrong, and the defect was mine.** My selection step deleted 1,035 rows from `mutation_specs` but
left all 1,047 parent rows in `work_items`; `WorkDB` rebuilds those orphans as
`WorkItem(mutations=())`, so `exec` ran mutation-free baselines and recorded each green run as
SURVIVED with an empty diff. Codex inspected the session DB and the WorkDB implementation and
proved it.

`diff == ""` on all twelve results was the tell and I read past it — a mutation result with no diff
is not a survivor, it is proof nothing was mutated. I blamed the tool before auditing my own
manipulation of its state: the same shape as "`pip index versions` proves installability" and
"`init` succeeds so the tool works." Verifying a component and generalizing to the whole is the
error this session keeps repeating.

The repair was Codex's, executed verbatim, and both rounds now enforce a post-run acceptance check
— exactly 12 results, **every** diff non-empty, outcomes summing to 12 — so a vacuous run cannot be
reported as a census again.
